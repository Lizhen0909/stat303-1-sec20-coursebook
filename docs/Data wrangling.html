14  Combining Datasets

The data you need for an analysis often lives in more than one table. To compare life expectancy across continents, for example, you may first need to combine five regional files. To study how life expectancy relates to income, you may need to bring measurements from two tables together for each country and year. Both tasks combine datasets, but they combine them in different ways.

This chapter introduces two operations: stacking rows with pd.concat() and matching rows with merge(). Stacking brings together observations spread across files with the same columns. Matching uses a shared key, such as country and year, to connect related information, even when the rows appear in a different order.

In Data Reshaping, you changed how values were arranged within a table. Here, you will bring separate tables together. Before each combination, ask: What does one row represent, and which rows belong together? Afterward, check the result: a command can run without errors and still leave out observations, create extra rows, or introduce missing values.

By the end of this chapter you should be able to:

  • Stack tables that share their columns with pd.concat(), record which piece each row came from, and check the row count.
  • Combine tables that share a key with merge(), on one or several key columns, including keys with different names (left_on=, right_on=).
  • Choose how= ("inner", "left", "right", "outer"), predict which rows survive, and use indicator=True to see where each row came from.
  • Check a merge before trusting it: compare row counts, enforce key uniqueness with validate=, and decide what the missing values from unmatched keys mean.

14.2 Stack or match?

Choose the operation by asking what the tables contain:

Your task Operation Tool What to check
Bring observations from separate files into one table Stack rows pd.concat() Column names agree; row counts add up
Attach related information using shared identifiers Match rows df.merge() The keys match the intended observations; the row count depends on the matches

14.3 Stack rows: pd.concat()

Start with two small tables that have the same columns. Each row describes one country in 2007. Put the tables in a list and pass that list to pd.concat():

africa_sample = pd.DataFrame({"country": ["Algeria", "Angola"], "year": [2007, 2007]})
asia_sample = pd.DataFrame({"country": ["Afghanistan", "Bahrain"], "year": [2007, 2007]})

pd.concat([africa_sample, asia_sample], ignore_index=True)
country year
0 Algeria 2007
1 Angola 2007
2 Afghanistan 2007
3 Bahrain 2007

The result has four rows and the same two columns. ignore_index=True gives the combined table a fresh sequence of row labels; it does not change the country values.

Now apply the same operation to the full Gapminder data: five files, one per continent, each with the same five columns. None has a continent column; that information is in the filename. The loop below reads each file, adds its continent, and collects the tables in a list. The final pd.concat() stacks that list just as it stacked the two small tables above.

pieces = []
for continent in ["Africa", "Americas", "Asia", "Europe", "Oceania"]:
    piece = pd.read_csv(f"data/gdp_lifeExpec_{continent}.csv")
    piece["continent"] = continent
    print(continent, piece.shape)
    pieces.append(piece)

gapminder = pd.concat(pieces, ignore_index=True)
print("stacked:", gapminder.shape)

624 + 300 + 396 + 360 + 24 = 1,704 rows: the stacked table has exactly the rows of its pieces, which is the check to make after any stack. ignore_index=True numbers the stacked rows 0 to 1,703; without it, each piece keeps its own numbering and row labels repeat.

concat() lines up columns by name. A column that some pieces lack is filled with NaN in the rows from those pieces. Suppose the Africa file had spelled one column differently:

renamed = pieces[0].rename(columns={"lifeExp": "life_expectancy"})   # the Africa piece
mixed = pd.concat([renamed] + pieces[1:], ignore_index=True)

print(mixed.columns.tolist())
mixed[["lifeExp", "life_expectancy"]].isna().sum()

No error, the right number of rows, and life expectancy split across two half-empty columns: lifeExp is missing for Africa’s 624 rows and life_expectancy for the other 1,080. Any analysis of lifeExp would silently leave out Africa. After stacking files you did not make yourself, check columns and count missing values per column.

The correctly stacked table goes straight into the tools of the last chapters:

fig, ax = plt.subplots(figsize=(8, 4.5), layout="constrained")

             errorbar=None, marker="o", ax=ax)
ax.set(xlabel="Year", ylabel="Mean life expectancy (years)",
       title="Five files, one table, one plot")
plt.show()

lineplot averages the countries of each continent in each year, as groupby() did in Data Grouping and Aggregation; errorbar=None leaves out the confidence bands. Without the continent column added during the loop, this plot would be impossible.

14.4 Match rows on a key: merge()

Stacking works best when column names agree. Matching uses a merge key: one or more columns whose values determine which rows pair across the two tables. A merge key can repeat; whether it should be unique depends on what one row represents. Two small tables about members of the Fellowship from The Lord of the Rings show how it works. One lists skills, the other ages, and both identify members by FellowshipID:

skills = pd.DataFrame({
    "FellowshipID": [1001, 1002, 1003, 1004],
    "FirstName": ["Frodo", "Samwise", "Gandalf", "Pippin"],
    "Skills": ["Hiding", "Gardening", "Spells", "Fireworks"],
})
ages = pd.DataFrame({
    "FellowshipID": [1001, 1002, 1006, 1007, 1008],
    "FirstName": ["Frodo", "Samwise", "Legolas", "Elrond", "Boromir"],
    "Age": [50, 39, 2931, 6520, 51],
})
print(skills, "\n")
print(ages)
   FellowshipID FirstName     Skills
0          1001     Frodo     Hiding
1          1002   Samwise  Gardening
2          1003   Gandalf     Spells
3          1004    Pippin  Fireworks 

   FellowshipID FirstName   Age
0          1001     Frodo    50
1          1002   Samwise    39
2          1006   Legolas  2931
3          1007    Elrond  6520
4          1008   Boromir    51

Frodo and Samwise appear in both tables; Gandalf and Pippin only in skills; Legolas, Elrond, and Boromir only in ages. merge() pairs rows whose key values are equal:

skills.merge(ages, on="FellowshipID")
FellowshipID FirstName_x Skills FirstName_y Age
0 1001 Frodo Hiding Frodo 50
1 1002 Samwise Gardening Samwise 39

Two rows: by default merge() keeps only keys found in both tables. Notice FirstName_x and FirstName_y. Both tables have a FirstName column that is not part of the key, so pandas keeps both and adds suffixes: _x from the left table, _y from the right. Here the two columns agree, because a name belongs to its ID.

14.4.1 Several key columns

Use several columns when they are needed together to identify the intended match. For Gapminder, a country appears in several years, so matching measurements requires both country and year. Here are three observations from the stacked data:

life_sample = gapminder[["country", "year", "lifeExp"]].head(3)
money_sample = gapminder[["country", "year", "gdpPercap"]].head(3)
life_sample.merge(money_sample, on=["country", "year"], validate="one_to_one")
country year lifeExp gdpPercap
0 Algeria 1952 43.077 2449.008185
1 Algeria 1957 45.685 3013.976023
2 Algeria 1962 48.303 2550.816880

Each life expectancy pairs with GDP for the same country and year. The validate="one_to_one" check requires that the pair of key values be unique in each table; we will examine validation below.

Choose keys from what a row represents, rather than including every shared column. FellowshipID already identifies a person, so adding FirstName is unnecessary and could prevent a valid match if the name differs between sources. Keep the two name columns when you need to compare them. Other genuine composite identifiers include store and date for a daily store summary, or student and course for a final course grade.

14.4.2 Keys with different names

Two sources rarely name their key the same way: FellowshipID in one file, ID in another. left_on= and right_on= name the key in each table:

ages_renamed = ages.rename(columns={"FellowshipID": "ID"})
skills.merge(ages_renamed, left_on="FellowshipID", right_on="ID")
FellowshipID FirstName_x Skills ID FirstName_y Age
0 1001 Frodo Hiding 1001 Frodo 50
1 1002 Samwise Gardening 1002 Samwise 39

Both key columns survive, holding identical values; drop one afterwards with .drop(columns="ID").

14.4.3 Which rows survive: how=

The rows that find no partner are where most mistakes happen. how= decides what happens to them:

The row counts in the diagram, 2, 4, 5, and 7, are worth confirming in code, and indicator=True adds a _merge column that says where each row came from:

fellowship = skills.merge(ages, on="FellowshipID", how="outer", indicator=True)

4 1006 NaN NaN Legolas 2931.0 right_only

Name: count, dtype: int64

both, left_only, and right_only describe whether a result row has a matching key in each source. Unexpected unmatched rows deserve investigation: they may reflect spelling differences, incomplete coverage, or genuinely different groups of records. With repeated keys, these are counts of result rows, not necessarily distinct people.

Which how= to use. Choose based on the records your analysis needs to retain:

An inner join introduces no missing values from unmatched keys, but existing missing values can remain in matched records. Left and right joins fill the other table’s columns with NaN where no match exists; an outer join can do this on either side. These row counts assume the unique IDs in this example. Repeated keys can create several output rows for one input row.

14.5 Check a merge

A merge can return a table of the right shape that is quietly wrong. Three checks catch most problems: the row count, the uniqueness of the keys, and the missing values that unmatched keys leave behind.

14.5.1 The row count, and keys that repeat

Suppose life expectancy and GDP arrived in two separate tables, both keyed by country and year:

life = gapminder[["country", "year", "lifeExp"]]
money = gapminder[["country", "year", "gdpPercap"]]

both_keys = life.merge(money, on=["country", "year"],
                       how="outer", validate="one_to_one", indicator=True)
print("rows:", len(life), len(money), "->", len(both_keys))
print(both_keys["_merge"].value_counts())
rows: 1704 1704 -> 1704
_merge
both          1704
left_only        0
right_only       0
Name: count, dtype: int64

All three checks agree: the result has 1,704 rows, validate="one_to_one" confirms unique country-year keys on both sides, and _merge reports 1,704 both rows with no unmatched rows. Together, these show that every observation found exactly one partner. The outer join makes unmatched rows from either source visible during this check.

The row count alone is not proof. In an inner join, one lost observation and one observation with two matches can cancel out, leaving the expected total. Validation checks how often keys occur; the indicator checks whether records matched.

Now try the same tables with an incomplete key, country alone:

country_only = life.merge(money, on="country")
print(country_only.shape)
country_only.head(3)
(20448, 5)
country year_x lifeExp year_y gdpPercap
0 Algeria 1952 43.077 1952 2449.008185
1 Algeria 1952 43.077 1957 3013.976023
2 Algeria 1952 43.077 1962 2550.816880

20,448 rows: twelve times too many, and no error. Each country has 12 rows in each table, so every row in life pairs with all 12 rows of the same country in money, and 12 × 12 = 144 rows per country × 142 countries = 20,448. The year_x and year_y columns are the giveaway: a 1952 life expectancy sits beside a 2007 GDP. For this task, the intended match is one country-year observation. country alone does not distinguish years.

validate= tells merge() what you expect and raises an error when the required key uniqueness does not hold. "one_to_one" means each key appears at most once in each table; "many_to_one" means the right table’s keys are unique, as for a lookup table. A try/except block shows the error and lets the notebook keep running:

try:
    life.merge(money, on="country", validate="one_to_one")
except pd.errors.MergeError as error:
    print("MergeError:", str(error).splitlines()[0])
MergeError: Merge keys are not unique in either left or right dataset; not a one-to-one merge.

The same check passes for the correct key, on=["country", "year"]. Add validate= whenever you know how the tables should relate; it turns a silent row explosion into an error you cannot miss. Before merging, df.duplicated(subset=key).sum(), from Data Cleaning, counts repeated keys in each table.

14.5.2 Many rows to one: a lookup table

The most common merge in practice attaches a small lookup table to many rows: a region for each state, a price for each product code, a group summary for each member. Each row of the large table can match at most one lookup row, while a lookup row can serve many rows — the "many_to_one" relationship. Validation requires unique keys in the lookup table; it does not require every key in the large table to find a match.

A summary from Data Grouping and Aggregation makes a lookup table: mean life expectancy for each continent and year, 60 rows. rename() gives its value column a distinct name before the merge:

continent_mean = (gapminder.groupby(["continent", "year"])["lifeExp"].mean()
                  .reset_index()
                  .rename(columns={"lifeExp": "continent_lifeExp"}))

with_mean = gapminder.merge(continent_mean, on=["continent", "year"],
                            how="left", validate="many_to_one", indicator=True)
print("rows:", len(gapminder), "->", len(with_mean))
print(with_mean["_merge"].value_counts())
rows: 1704 -> 1704
_merge
both          1704
left_only        0
right_only       0
Name: count, dtype: int64

validate="many_to_one" passes because each continent-year appears once in the lookup table. With how="left", that uniqueness guarantees that the 1,704 input rows are retained without duplication. The indicator separately confirms that all 1,704 rows found a match. A left lookup merge can keep the correct row count even when some keys are absent from the lookup; validation alone would not catch those missing matches.

Each country can now be compared with its continent in the same year:

with_mean["gap"] = with_mean["lifeExp"] - with_mean["continent_lifeExp"]
(with_mean.sort_values("gap")
    [["country", "continent", "year", "lifeExp", "continent_lifeExp", "gap"]]
    .head(3).round(1))
country continent year lifeExp continent_lifeExp gap
464 Rwanda Africa 1992 23.6 53.6 -30.0
965 Cambodia Asia 1977 31.2 59.6 -28.4
934 Afghanistan Asia 2002 42.1 69.2 -27.1

The largest gaps below a continent’s mean are Rwanda in 1992, 30 years below Africa’s mean in the years of its civil war and genocide; Cambodia in 1977, under the Khmer Rouge; and Afghanistan in 2002. The continent_lifeExp column is exactly what groupby(["continent", "year"])["lifeExp"].transform("mean") gave in Data Grouping and Aggregation. transform() is the shortcut when the summary comes from the same table; merging a summary back is the general pattern, and it works when the lookup table comes from somewhere else.

14.5.3 Missing values from unmatched keys

A merge can introduce NaN where a key has no partner. A matched record can also contain a value that was already missing in the source. Use indicator=True to distinguish these cases; isna() alone cannot tell you why a value is missing.

left_join = skills.merge(ages, on="FellowshipID", how="left", indicator=True)
left_join
FellowshipID FirstName_x Skills FirstName_y Age _merge
0 1001 Frodo Hiding Frodo 50.0 both
1 1002 Samwise Gardening Samwise 39.0 both
2 1003 Gandalf Spells NaN NaN left_only
3 1004 Pippin Fireworks NaN NaN left_only

Gandalf’s and Pippin’s ages are NaN because the ages table has no row for them, not because their age is zero. Three choices, from Data Cleaning:

  • Keep the NaN when absence is informative and should be reported, as here: the ages table is incomplete.
  • Fill only when absence has a known meaning. If purchase records are complete for the period and customer IDs match reliably, no purchase record can mean $0 spent. Fill those unmatched spending values with zero; do not automatically fill every missing value or use zero for an unknown age.
  • Drop with dropna(subset=[...]) when an analysis requires observed measurements, and report the exclusions. This can also remove matched records whose measurements were already missing. An inner join only requires matching keys; it does not ensure complete measurements.

Whichever you choose, count how many rows were unmatched before deciding.

Notejoin() and concat(axis=1)

You will also meet df.join(other), which matches rows on the index rather than on a column, and pd.concat([a, b], axis=1), which places tables side by side by index. Both do work merge() can do once the key is an ordinary column, which is how this book writes it: merge() names the key, so the match is visible in the code.

14.6 Summary Cheat Sheet

Stacking.

Goal Code
Stack tables with the same columns pd.concat([a, b, c], ignore_index=True)
Record each piece’s source piece["source"] = name before stacking
Check the result rows equal the sum of the pieces; inspect columns

Matching.

Goal Code
Match on one key left.merge(right, on="key")
Match on several keys left.merge(right, on=["k1", "k2"])
Keys with different names left.merge(right, left_on="id", right_on="ID")
Keep unmatched rows how="left", "right", or "outer" (default "inner")
See where each row came from indicator=True, then df["_merge"].value_counts()
Enforce how keys relate validate="one_to_one" or "many_to_one"
Count repeated keys first df.duplicated(subset=["key"]).sum()
Attach a lookup table big.merge(lookup, on="key", how="left", validate="many_to_one"); rows unchanged

The rule to remember: after every merge, compare the row count with what you expected and count where the rows came from.

14.9 Before You Move On

The habit to carry forward is checking every combination. A stack should have exactly the rows of its pieces. A merge should have the rows you predicted from its keys and its how=, and indicator=True and validate= turn the ways it can go wrong — unmatched keys, keys that repeat — into numbers and errors you can see. None of these mistakes raises an error on its own; a merged table looks complete whether or not it is right.

The other habit is asking what an absence means. A NaN from an unmatched key says the other table had no row, which is different from a value of zero and different from a measurement that was never taken.

For any combination you make, you should be able to answer five questions:

  1. Are you stacking tables with the same columns, or matching tables on a key?
  2. What are the merge keys, and are they unique in the left table, the right table, or both?
  3. Which how= did you choose, and how many rows did you expect?
  4. How many rows matched, and why did the others not?
  5. What do the missing values from unmatched keys mean, and what did you do with them?

This chapter completes the path the book has followed: reading data, cleaning it, preparing it, summarizing it by group, reshaping it, and now combining it. The assignments in the appendices bring these steps together on larger datasets.
